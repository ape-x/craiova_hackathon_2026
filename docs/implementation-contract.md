# Live assisted recovery — implementation contract

Updated 1 November 2026. FastAPI owns the validated schema, operational state and allocation checks; React consumes the same versioned state. This contract describes the shipped live assisted workflow, with pending work explicitly separated. See [product scope](product-spec.md), [live data](live-mode.md) and [verification](verification/report.md).

## State and provenance

- `World.mode=live` starts with a real airport reference and no passenger or supplier inventory. The persistent operation is never reset by opening a case or running a search.
- `Airport.kind` is `airport`, `station`, `hotel` or `meeting_point`. Properties, stations and declared meeting points are physical nodes, never airport/diversion targets. Supplier hotel coordinates and their derived local time zone remain attached to the property.
- `PassengerGroup.source` distinguishes imported passengers, operator input and generated planning assumptions. Generated groups cannot receive real external booking confirmations.
- `RecoveryIncident` holds the operator's report, exact flight selection reference and explicitly linked groups. `incident.flight` is transient FR24 context; expiration does not delete the operator's case.
- `Resource` represents a dated, sourced service. Quote-specific price/capacity scope is preserved; geography, road estimates and FR24 observations do not manufacture inventory.
- Live offer states distinguish `proposed`, passenger `accepted` and externally `confirmed`. Local reservations coordinate proposals inside the app; they are not supplier holds.

## Operator reports and continued live operation

The case panel accepts an explicit arrival report with `group_ids`, known `airport_code`, minute-precision timezone-aware `ready_at`, `description`, version and idempotency key. Only reciprocally linked groups move to the declared starting airport/readiness; destination, deadline, passenger identity and original flight remain unchanged. A readiness after the deadline stays visible as an unmet constraint. An arrival report is operator data, not FR24 landing confirmation or airport operating permission. A newly referenced airport is catalog geography with unknown operational status. Only the selected groups' proposed/accepted offers are invalidated. Existing hotel profile bytes remain as history; changed route identity prevents stale reuse.

The live resource inspector accepts an unavailable-service report with description, version and key. It sets that exact resource unavailable for planning, records operator provenance and receipt time, and invalidates only dependent proposed/accepted offers. Supplier prices, dates, source evidence and booking records remain unchanged. Both report paths reject impacts on externally confirmed bookings before mutation, requiring separate operator review. Reports and receipts preserve actual affected groups/offers. Unknown submission outcomes retain the original serialized request/key. Neither form starts a source call or a replan; review the updated case and request recovery separately.

The voice/text command bridge can record one of these reports and, only when the same current request explicitly asks for it, queue scoped recovery. An arrival report must name the current case/flight and exact linked groups, an unambiguous airport, and passenger readiness. Absolute readiness needs a full date, `HH:mm`, and UTC or a numeric offset. Alternatively an explicit current phrase such as `in N minutes`, `în N de minute` or `peste N minute` accepts integer minutes 0–10080. The server rounds the command's durable pre-interpretation receipt time up to UTC minute precision and adds the stated interval. `report.readiness_basis` preserves the reference, command receipt, rounded anchor, interval and `rounding:ceil_minute` in the receipt, audit and per-group history. A replay or model/browser clock cannot reanchor it. Bare “now”, unstated dates/timezones, conflicting times and inferred delays require clarification; a flight's diversion, ETA or inability to land does not establish passenger readiness.

A service report must name its exact resource ID or unique current name; repeated vehicle names need the ID. Negations, questions, conditional claims and ambiguous references produce clarification without applying part of the request. Explicit operator planning assumptions remain labelled operator data. Context and prior utterances cannot supply missing scope or a spending allowance.

The response has `applied:true` only when the report persisted, `report` with `source:operator_report`, and `command_interpretation_calls:1`. That flag does not mean a recovery plan or booking exists. Report-only responses omit both `recovery_job` and `recovery_blocked`. A combined request adds its `recovery_total_call_limit` and either an actual `recovery_job` receipt or `recovery_blocked:{code,explanation}`. Known blocks are `insufficient_call_allowance`, `hotel_setup_required`, `recovery_prerequisite_failed` and `recovery_queue_unavailable`: the valid report remains recorded, but no job or supplier search is dispatched. Arrival-plus-recovery uses exactly the reported case/groups and validates any saved hotel setup against the post-report world. No inferred pickup, deadline extension or cap increase repairs it. The report, optional queued job and command receipt commit atomically; unexpected transaction failure rolls them back together.

Generic manifest, planning-passenger and manual-service imports are additive. They preserve existing proposals and allocations; source quote replacement still invalidates its explicit affected scope.

Live timestamps retain the original epoch and all stored absolute instants. The upper planning bound is seven days from the current server-derived operation minute, so an operation older than a week can still accept future manifests, services, quotes and full hotel packages. Source-specific future/readiness/deadline checks remain in force. The passenger deadline editor uses explicit UTC dates and contextual limits; it does not advance an expired deadline automatically. The internal simulation retains its fixed seven-day horizon. Historical resource/node caps remain separate capacity limits and still need an archival lifecycle for prolonged accumulation.

## Durable recovery jobs

Start input: `group_ids` (1–24), `objective` (`balanced`, `fastest`, `lowest_cost`), requested `modes`, `max_provider_calls` (3–26), `instructions`, expected world version and idempotency key. Every selected group must already belong to the case; externally confirmed groups require separate operator handling.

Job statuses: `queued`, `running`, `completed`, `blocked`, `failed`, `cancelled`, `needs_review`, `unknown_outcome`. Stages: validation, query planning, supplier searches, evaluation, Decisions selection and atomic application. The ledger records each actual dispatch, outcome, quote count and affected group selection. Jobs are separate from `World` and survive reopening the case.

Without `hotel_recovery`, automatic sourcing covers flight offers. Responses selects eligible dated queries; independent supplier searches can run concurrently. Deterministic code builds and checks complete itineraries; Decisions selects among valid candidates. Existing complete sourced ground/hotel links can participate. Missing stay inputs, ground connections, fare currency or dated transport information produce explicit gaps.

Optional `hotel_recovery` fields are `checkin_at`, `checkout_at`, `rooms`, `minimum_rest_minutes`, `initial_point:{label,latitude,longitude,confirmed:true}`, `pickup_at`, `suitcases`, `onward_airport_code`, `airport_dropoff:{label,latitude,longitude,confirmed:true}` and `airport_processing_minutes`. Times must have an explicit offset and whole-minute precision. Rooms are strict integers 1–30, suitcases 0–200, processing minutes 1–720; the requested rest must fit the stay. The request selects exactly one explicitly adult-only group and all three modes (`flight`, `hotel`, `bus`), with supported UK initial/onward airports and no unsupported accessibility requirement. Future times, readiness, deadline, room occupancy and the seven-day horizon are validated before dispatch.

The typed hotel flow requires an explicit `max_provider_calls>=10`; default eight is unchanged. Its conservative allowance counts one Responses selection, one flight search, one hotel-rate search, one exact property metadata request, two APL quotes, two Google dated routes, one ECB request and one Decisions selection. Independent sources run with maximum concurrency three, each through its own durable ledger step. One complete-price property is shortlisted and one onward flight date is searched (checkout's Europe/London date); at most three fitting vehicle options per direction are compared. A rejected property does not trigger an unrequested alternative-property search. Exact source flight times are filtered against post-stay readiness/deadline before the provider's price shortlist, then checked against actual driving and processing time.

The successful plan has four resources: initial private transfer, sourced hotel stay, private return transfer and exact onward flight. Return pickup is checkout plus a ten-minute application allowance. Sourced policy validation, full mandatory hotel costs, physical addresses/coordinates, typed GBP/ECB estimates and live receipt windows remain mandatory. Only chosen source nodes/resources and selected-group requirements/offers are committed, atomically with the job result after current version/scope/freshness validation. No booking occurs. `result.hotel_recovery` is present only for a complete successful package and contains `hotel_id`, `hotel_node_id`, `hotel_shortlist_limit:1`, `flight_query_date`, `return_pickup_at`, `return_pickup_basis:'checkout_plus_10_minute_app_allowance'` and `required_provider_calls:10`.

`result` records plan/decision references, proposed and exception passenger counts, offer/service references, source counts and optional waiting intervals. These are historical result counts at `applied_version`; the frontend separately checks which offers remain active. `quote_not_usable` and `no_flight_offers` are source/search exclusions, not automatically unresolved passenger requirements. Overnight-wait notes remain informational unless an explicit applicable requirement says otherwise.

The live solver supports up to six itinerary legs, including physical hotel transfers. It validates elapsed time and dates; it does not apply the internal simulation's epoch-day rule as a mandatory live hotel requirement. Waiting summaries use the actual location's time zone when known and disclose unknown zones. The optional typed `group.provenance.hotel_stay_requirement` records operator-requested check-in/out, exact rooms and minimum rest. One actual sourced stay must cover the whole interval; disjoint stays or waiting cannot substitute. Free-form instructions alone do not establish this constraint. A hotel alone is never a recovered journey.

## Manual hotel import and stay policy

The hotel-import request shape is unchanged. With `stay_times_confirmed=false`, the server fetches metadata for the exact property even when the rate already contains coordinates, bounded to ten properties with concurrency three. Property-coordinate IANA time zones and the pinned time-zone data anchor the supplied check-in window and checkout cutoff to the quoted dates. A bounded check-in window may span midnight; absent `checkin_end`, only the exact published start is automatically accepted.

Missing, unsupported or conflicting policy times, special check-in instructions, source/property identity or freshness mismatches, and ambiguous/nonexistent daylight-saving boundaries exclude the property with a reason. Successful provenance contains `stay_times_source='supplier_policy'`, `stay_times_confirmed=false` and `stay_policy_validation` with source, property ID, time zone and dated bounds. `stay_times_confirmed=true` remains a separate `operator_confirmed` declaration that the stay times were agreed with the property; it is not a supplier booking.

The response preserves `skipped_incomplete_pricing` and adds `skipped_stay_policy` and `hotel_exclusions[{hotel_id,code,message}]`. If every option is excluded, HTTP422 leaves the operation unchanged. No policy result implies a shuttle, physical transfer or reserved room. Live UI import verified nine eligible property/quote pairs with the operator override false and one policy exclusion. A later automatic job separately verified the complete sourced hotel-and-transfer proposal, as recorded in the [verification report](verification/report.md).

## Manual private-transfer planning

**Private transfers** supports manual initial UK airport-point → hotel and hotel → UK airport directions, subject to connected supplier coverage. Both require an explicitly adult-only group without unsupported accessibility/child-seat requirements, an explicit suitcase count, and a future minute-aligned pickup with UTC offset. Pickup must respect the group's readiness/deadline and the existing operation horizon. Ambiguous repeated London clock times are rejected. These manual searches do not refresh hotel-room availability or establish a complete recovery; the separate optional hotel job above sources and validates the whole chain.

Outbound search input is `group_id`, `hotel_node_id`, `pickup_at`, `suitcases`, `initial_point:{label,latitude,longitude,confirmed:true}`, `expected_version` and `idempotency_key`. Party size and airport context come from the existing group; the browser cannot submit a price, duration or substitute hotel address. The server fetches the exact LiteAPI property ID and reconciles its coordinates with the stored hotel node. Missing usable postal metadata blocks further sourcing. APL's exact request retains that address and the declared pickup. Conflicting returned airport, direction, terminal or destination evidence blocks import; absent supplier fields remain unknown. Address comparison preserves street-number, city and postcode boundaries rather than guessing aliases.

That request remains the default `direction='initial_airport_to_hotel'`. For `direction='hotel_to_airport'`, omit `initial_point` and supply `airport_dropoff:{label,latitude,longitude,confirmed:true}`, `onward_resource_id` and integer `airport_processing_minutes` (1–720). The exact onward flight must be current, available, unbooked, sourced and eligible exclusively for the group, with matching supplier identity/departure evidence and valid incident/airport constraints. The UI exposes stale quotes as requiring refresh; it never chooses an ambiguous first match. The server checks predicted road arrival plus the declared processing allowance against that flight's departure. The allowance is operator input, not airline guidance or a boarding guarantee; `departure_terminal` remains null.

The response contains `quote_id`, `state` (`ready` or `blocked`), `direction`, group/property references, `source_version`, `created_at`, `usable_until`, sourced `hotel`, nullable `transfer`/`route`, `blockers`, per-option importability and `replayed`. `initial_point` is null on return; `airport_arrival_assumption` and `onward_flight` carry the declared drop-off/buffer and exact flight reference, and are null outbound. Optional `transfer.meeting_point:{name,instructions}` is separately attributed APL pickup guidance, never evidence of a flight terminal. Expected supplier or route failures preserve successful source results and return visible blockers. Invalid input or a stale initial version fails before paid source work.

The Google-only `dated_route` request includes the actual future pickup and exact requested coordinates. Return geometry ends at `airport_arrival_assumption.dropoff.coordinates`, not the airport catalog reference. It retains decimal-string seconds, integer metres, receipt time, requested and road-snapped endpoints, warnings and optional bounded `encoded_polyline`; no current-time or OSRM substitute is used. The importer rounds arrival upward to an operation minute. Both times and geometry are source predictions, not proof of loading, walking or terminal access. Application screens reject a declared airport point more than 10 km from its catalog airport reference and a Google road endpoint more than 100 m from its requested point; these are disclosed screening limits, not supplier guarantees.

Import input is `option_id`, `policy_id:'ecb_reference_v1'`, `expected_version` and `idempotency_key`. The verified cache supplies all money and route evidence. Outbound import creates a distinct `MP-…` meeting-point node and a group-only `Resource` with internal ground kind `bus`, `transport_mode='private_transfer'`, and `capacity_scope='private_vehicle_quote'`. Capacity represents the quoted party, not fleet stock or additional seats for sale. `initial_position_assumption` records operator input and a group/scenario fingerprint. The solver may use this point only as that group's first leg; `group.origin` is unchanged and no synthetic airport-to-point edge is added.

The meeting-point exemption applies only outbound. A return resource uses the actual hotel node as `origin` and the onward flight's airport IATA node as `destination`; it creates no new meeting-point node. Its typed `airport_arrival_assumption` is copied to the leg and binds the group/scenario, exact flight revision and departure, declared drop-off coordinates, processing minutes and null terminal. The solver requires the exact bound flight immediately after the return and preserves the operator-buffer disclosure in passenger/Decisions evidence. A return cannot teleport a group to the hotel.

Immutable revisions preserve source facts. A newer import retires replaceable earlier APL revisions for the same group and direction; source records for the other direction remain. Dependent replaceable proposals may be invalidated atomically, while unrelated offers and confirmed bookings stay protected. An older cached quote cannot replace an already imported newer revision. Resource evidence is copied into itinerary legs and retained in passenger/decision evidence. Import alone creates no offer, supplier hold, booking or recovered-passenger count. Original GBP and the explicitly estimated ECB EUR component remain distinct throughout.

## Mutation, retry and budget boundaries

SQLite is authoritative for versions, allocations, the job ledger and idempotency. Provider calls occur outside world transactions; a compare-and-apply step rechecks source freshness and current constraints before committing. Scoped jobs preserve all out-of-scope allocations, including proposed and accepted ones.

Replay of a job-start key returns its current job without another provider call. Unknown outcomes require review and an explicit new attempt, not an automatic billed retry. Cancellation prevents subsequent dispatch/application; it cannot undo a dispatched provider call. This is not an upstream exactly-once billing guarantee.

Existing request claims can return HTTP503 with `applied:null`, `details.in_progress=true` and `Retry-After`. Clients retain the original serialized payload/key while the result is uncertain. Definitive conflicts unlock editing after refresh; changed payloads receive new keys. Passenger authorization is checked before cached replay, and stale/revoked tokens cannot expose a prior operation.

Ordinary EUR quote checks require documented complete costs; missing mandatory hotel fees still prevent a fully calculated hotel budget. Explicitly imported APL legs use the accepted `ecb_reference_v1` planning policy. `Resource.price_evidence` and `Leg.price_evidence` retain exact original GBP, the dated ECB EUR estimate, per-vehicle scope, `settlement_guaranteed=false` and `revalidation_required=true`. `Itinerary.cost_evidence` and `Plan.cost_evidence` identify estimated components. The legacy numeric EUR fields support planning comparisons, not a supplier EUR charge; GBP is never placed in `quote_total_cost`. Decisions and passenger/operator totals preserve the distinction. Currency settlement and the supplier price must be revalidated before booking; no automatic buffer or extra budget is introduced.

Successful APL quote responses include `fx` with `ready`, `unavailable`, `stale_rate`, `missing_rate` or `not_requested`, source metadata, reference date/assessment and cache status. The explicit app policy allows at most three calendar days of rate age in Europe/Berlin. Each option retains its original `price` and adds `eur_reference_estimate` or null. The server uses Decimal and half-even cent rounding; the browser displays the provided amount without recalculating it. Missing/stale FX preserves GBP, suppresses EUR and prevents planning import. No silent fallback rate or guaranteed supplier EUR price is introduced.

Transfer-search dispatch is recorded durably before external work. A repeated key with identical inputs returns the cached result without another dispatch; changed inputs conflict. In-progress and unknown dispatches return HTTP503 with `applied:null`; an unknown outcome never becomes an automatic billed retry. The transient source cache holds at most 64 responses with a maximum 120-second window, bounded further by pickup/source usability. Expired searches cannot be reissued through the same key. A completed import can still replay its historical mutation receipt after that cache expires. Backups remove the source cache and mark in-flight receipts unknown; restoring a backup does not resume searches.

## Rendering and source separation

`Scene` receives `world`, selection and camera mode; Google Maps provides geographic rendering when available. The native Three.js scene and authored GLBs retain their illustrative provenance. Live scheduled inventory is not drawn as tracked passenger/vehicle motion. FR24 observations, physical location nodes and their source timestamps remain distinct from proposals.

Google TRANSIT currently has a pure request/response adapter and offline tests only. Stops and schedules do not establish seat availability; incomplete fares remain unknown, and missing walking durations do not pass a walking limit. There is no connected public-transit inventory or automatic booking path.

Passenger itineraries expand validated supplier flight segments and connection waits. Source-local clocks include explicit UTC offsets; missing local clocks use labeled UTC. Source endpoints must reconcile with the epoch and authoritative resource/offer-leg times using departure-floor and arrival-ceiling minute bounds. Invalid calendar dates or inconsistent provenance use the explicitly labeled Europe/Bucharest operations-time summary instead. The passenger arrival summary uses the same validated final segment.

Live resource freshness presentation mirrors the backend. APL uses typed `quote_freshness:{basis:'app_receipt',received_at,max_age_seconds:120}`; its supplier quote time and expiry remain null. Return planning also requires a valid non-future `google_route.fetched_at`: its cutoff is the earlier of the APL and Google receipt plus 120 seconds, inclusive at the boundary. Both receipt times and the combined cutoff are shown in UTC; missing/malformed evidence is not current. Other sourced quotes retain their explicit validity or source-time rule. Invalid explicit validity does not fall back to source time. Neutral headings and stale/unknown labels replace ordinary capacity claims when unusable. The local clock updates without network calls; these windows are app policy, not supplier expiry. Unavailable/superseded states retain precedence and recorded bookings remain separate from quote age. The backend remains authoritative.

## AI and voice status

Voice startup can carry only selected case/group IDs. The open case takes precedence; otherwise the selected group resolves its reciprocal case, or the last explicitly opened valid case remains reference context after the dialog closes. No selection omits scope. The server resolves bounded canonical facts into GPT-Live `session.input`, rejects invalid references before provider creation and retains unchanged command/transcript validation. This is reference context, not permission to execute; it never supplies a spending allowance, silently corrects a spoken date or claims a booking. The implementation is covered offline; its effect on live recognition remains unverified.

The scoped voice/text-to-job bridge is implemented. The current request must name an existing case ID or an unambiguous flight, with a date when needed to distinguish cases. Only already-linked groups are eligible; externally confirmed groups are protected. A recovery intent does not invoke a global replan. A queued receipt includes `incident_id`, `recovery_job`, `command_interpretation_calls` and `recovery_total_call_limit`; the UI opens the matching case and polls the existing job panel.

The default command allowance is eight calls total: one interpretation plus at most seven job calls. A stated limit of four permits one interpretation plus three job calls; a limit of three or less prevents a job. A valid combined report can still be recorded with the insufficient-allowance result described above; a recovery-only request returns clarification. A literal zero prevents even interpretation. The manual form's default allowance remains eight job calls. Parsed intent is cached, job creation and the command receipt are atomic, and unknown/crashed interpretation is never automatically reissued.

Voice acknowledgements use the structured receipt, not another interpretation. Within the existing 480-byte UTF-8 commentary limit they distinguish the recorded operator report, recorded search request, known blocked search, and report-only result. They retain the declared airport/readiness/group count or exact affected service and reserve space for the qualification about airport clearance, supplier cancellation and bookings. A replay says already recorded: a durable receipt's old `queued` status is not current progress. The case panel supplies current job status; no spoken acknowledgement claims a completed journey or a still-valid proposal. Unknown transport outcomes remain unknown, with manual **Recover request** reusing the original transcript, context, serialized body and idempotency key. Neither the client nor prior dialogue silently retries with a new key or raises the call cap. These report/acknowledgement paths have offline coverage; no paid voice or microphone verification is claimed.

Hotel voice/text reuse requires one exact group, flight/hotel/bus modes, an explicit allowance of at least eleven total calls and a valid saved `hotel_recovery_profile`. A profile is saved only with a complete successful typed hotel plan. Its schema is `{schema_version:1,source:'operator_requested',scope_fingerprint,inputs:<exact HotelRecoveryInputs>}`. Identity binds the scenario/epoch, reciprocal case/group membership, flight/date and party/route identity. Mutable readiness, deadlines and budgets are not frozen: the current values and all saved inputs are revalidated before job dispatch. Profile data is installed identically before both projected and committed transfer fingerprints. Failure or rollback cannot replace it. Missing/stale identity or a request to alter saved inputs requires the typed form; dates, coordinates, bags and buffers are not guessed. Neither the eleven-call requirement nor the typed ten-call requirement raises the default eight automatically.

## Data handling and internal modes

Provider secrets remain server-side; the Maps browser key is explicitly public and requires separate origin/API restrictions. Temporary FR24 context is stripped from portable exports, idempotency snapshots and operational backups. Public verification records omit raw provider payloads, private case/job/group references, passenger tokens, account contacts and credentials.

The sole active application is the persistent local instance on port 8080. Internal simulation fixtures and their reset semantics are retained for regression tests, not as a fallback for missing live supply. Source modules and schemas remain the authority if this summary lags a subsequent version.
